# S3

How to deploy a `storage/s3` block, reach it with an S3 client, and what a client sees when the
node serving it fails.

## 1. The design, in one paragraph

`storage/s3` serves an S3-compatible API from [Garage](https://garagehq.deuxfleurs.fr/), run as a
single-node Garage on a DRBD-backed volume. It is active/passive like `share/nfs`: the block is
`SINGLETON`, it runs only where the volume's DRBD primary is, and it is reached through a stable
external VIP (`EXPOSE_VIP`). Everything Garage keeps lives on the volume under `.garage/`: its
metadata database, the object blocks, its node key, and the RPC secret and admin token the block
generates on first start. The node that takes over after a failover is therefore the same Garage
node, with the same layout, keys and buckets. Replication is DRBD's job, so Garage runs with
`replication_factor = 1`, its metadata in LMDB, and fsyncs metadata and data before
acknowledging a write. Garage's sqlite engine is not used: it does not sync each commit, and the
first crash test lost acknowledged objects with it.

## 2. Deploying

```yaml
apiVersion: expanse.io/v1
kind: Block
metadata:
  name: objects
  namespace: default
spec:
  type: storage/s3
  replicas: 1
  strategy:
    kind: SINGLETON
  resources:
    requests:
      cpu: 100m
      memory: 256Mi
  storage:
    - name: objects-data
      size: 100Gi
      replication: 3
      mountPath: /var/lib/s3
  config:
    port: 13900          # Garage's own S3 port; never 3900 (see below)
    accessKeyId: GK0123456789abcdef01234567
    secretAccessKey: 0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef
    buckets: [media, backups]
  network:
    ports:
      - name: s3
        port: 3900
        target_port: 13900
        protocol: tcp
        expose: EXPOSE_VIP
    health_check:
      readiness:
        type: PROBE_TCP
        port: 13900
        period_seconds: 2
```

Generate the key pair once and keep it:

```sh
echo "accessKeyId: GK$(openssl rand -hex 12)"
echo "secretAccessKey: $(openssl rand -hex 32)"
```

`config.port` must differ from the exposed port: the VIP holder binds `VIP:3900` on the very node
Garage runs on.

| Key | Default | Meaning |
|---|---|---|
| `accessKeyId` | required | `GK` followed by 24 lowercase hex digits |
| `secretAccessKey` | required | 64 lowercase hex digits. Fixed once the key exists on the volume |
| `buckets` | `[]` | Buckets created on start and granted to the key (read, write, owner) |
| `region` | `garage` | Region clients sign requests for |
| `port` | `13900` | Garage's S3 listen port (`target_port`) |
| `rpcPort` | `13901` | Garage's internal RPC port, on localhost only |
| `adminPort` | `13903` | Garage's admin API port, on localhost only |

On every start the block gives the node its layout role (first start only), imports the key,
creates any missing bucket and grants it to the key. Changing `buckets` and redeploying adds the
new ones; removing a name does not delete the bucket. Garage cannot re-import a key id with a
different secret, so a changed `secretAccessKey` makes the block fail to start with an error
naming it; deploy with a new `accessKeyId` instead.

The key may also create its own buckets. Garage keeps those as the key's private aliases: they are
not in `buckets` and the admin API lists them under the key, not globally.

Two instances on one node need distinct `port`, `rpcPort` and `adminPort`. Each node must have
`pkgs.garage` in `environment.systemPackages`.

## 3. Clients

Use path-style addressing (`http://<VIP>:3900/<bucket>/<key>`) and the configured region. With
the AWS CLI:

```sh
export AWS_ACCESS_KEY_ID=GK0123456789abcdef01234567
export AWS_SECRET_ACCESS_KEY=0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef
export AWS_DEFAULT_REGION=garage
aws --endpoint-url http://<VIP>:3900 s3 cp ./file s3://media/file
```

or curl alone:

```sh
curl --aws-sigv4 aws:amz:garage:s3 --user "$AWS_ACCESS_KEY_ID:$AWS_SECRET_ACCESS_KEY" \
  -T ./file http://<VIP>:3900/media/file
```

restic takes `s3:http://<VIP>:3900/backups` as its repository.

**Security.** The API is plain HTTP; requests are signed, but the payload is not encrypted. Keep the
VIP on a network you trust or put a TLS-terminating proxy in front of it. The admin API is bound
to localhost and is not exposed.

## 4. Failover, from a client's perspective

When the node serving the block dies, the block, its volume's DRBD primary and its VIP move
together to a survivor. Requests sent in the meantime fail with a connection error or time out;
clients retry against the same endpoint and key. Object data is synced, file and directory, before
Garage acknowledges a write. Metadata commits are synced too, with one gap: Garage opens LMDB with
`MDB_NOMETASYNC`, so a crash can undo the very last metadata commit. Garage commits continuously
in the background, so this window is short, but a client that must not lose a write should read
it back after a failover. The block also creates Garage's node key itself and syncs it, because
Garage writes that file without a sync and a lost key would make the survivor a different Garage
node.

Measured in the `storage-s3` VM test (3 nodes, 5 s agent period): the block, primary and VIP
agreed on a survivor 58 to 62 s after the serving VM was killed, and a client retrying failed PUTs
had its writes acknowledged again under a second later. Every acknowledged object and an 8 MiB
object written before the failure read back intact.

## 5. What is not covered

- TLS, virtual-host-style bucket addressing and Garage's static website hosting.
- More than one access key, and per-bucket permissions narrower than read, write and owner.
- Garage's own multi-node replication: one block is one Garage node, replicated by DRBD.
- Quotas: size the volume instead.
